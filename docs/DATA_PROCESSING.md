# Data Processing Guide

This guide provides an overview of the data processing pipeline and the various fixes and transformations applied to TSV files in this repository.

## Overview

The BGE skimming analytics project processes genome skimming validation outputs to create standardized, high-quality datasets. Raw data files often contain inconsistencies, non-standard column names, or missing derived columns that need to be addressed before the data can be published as FAIR data packages.

## Data Sources

TSV files in this repository are generated by the [barcode validator](https://github.com/naturalis/barcode_validator) and collected from:

- **Naturalis Biodiversity Center**: Files in `data/naturalis/`
- **Natural History Museum London**: Files in `data/nhm/`

Files are organized by processing approach:
- `1step/`: Single-step validation approach
- `2step/`: Two-step validation approach
- Within each: `6p/`, `24p/` subdirectories indicate the number of parameters used

## Metadata Specification

All column headers must conform to the definitions in `metadata/headers.tsv`. This file defines:
- Standard column names
- Data types and formats
- Whether columns are compulsory or optional
- Column descriptions

The metadata specification follows [frictionless data](https://frictionlessdata.io/) standards.

## Data Processing Pipeline

The data processing workflow consists of several steps, each addressing specific issues:

### 1. Column Standardization

**Issue**: Non-standard column names that don't match the metadata specification.

**Scripts**:
- `fix_process_id_column.py` - Renames or removes `process_id` columns ([details](PROCESS_ID_FIX.md))
- `fix_n_aligned_column.py` - Renames `n_aligned` to `n_reads_aligned` ([details](N_ALIGNED_FIX.md))

**Why**: Column names must exactly match the metadata specification for validation and downstream analysis.

### 2. Redundant Column Removal

**Issue**: Some files contain columns that duplicate information available in other columns.

**Scripts**:
- `fix_filename_column.py` - Removes redundant `Filename` columns ([details](FILENAME_FIX.md))
- `remove_backbone_source_column.py` - Removes `backbone_source` columns

**Why**: Redundant columns increase file size and can cause confusion about which field is authoritative.

### 3. Structured Data Parsing

**Issue**: Some columns contain structured data (like `PROC_r_1.3_s_100`) that should be split into separate fields for analysis.

**Scripts**:
- `parse_sequence_id_columns.py` - Extracts `group_id`, `r`, `s` from `sequence_id` patterns ([details](SEQUENCE_ID_PARSING.md))
- `parse_mge_params_columns.py` - Extracts `r`, `s` from `mge_params` patterns ([details](MGE_PARAMS_PARSING.md))
- `add_fcleaner_merge_columns.py` - Adds boolean flags for data processing steps ([details](FCLEANER_MERGE_COLUMNS.md))
- `add_metadata_columns.py` - Adds metadata columns (`inst`, `validation_steps`, `assembly_params`) based on directory structure

**Why**: Separating structured identifiers into components enables filtering, grouping, and analysis by individual parameters. Metadata columns capture information about the institute, validation procedure, and assembly parameters used.

### 4. Data Merging

**Issue**: Assembly metrics and validation results are sometimes stored in separate files that need to be combined.

**Scripts**:
- `merge_6p_data.py` - Merges TSV validation files with CSV assembly metrics ([details](1step_6p_merge_report.md))
- `bv_metrics_merger.py` - General-purpose merger for barcode validator outputs

**Why**: Complete records combining validation results with assembly metrics provide a comprehensive view of data quality.

### 5. Quality Control

**Issue**: Some rows represent negative controls or test data that should not be included in final datasets.

**Scripts**:
- `remove_negative_controls.py` - Removes negative control rows

**Why**: Published datasets should contain only real sample data.

### 6. Coverage Analysis

**Issue**: Not all files contain the full set of expected columns.

**Scripts**:
- `analyze_tsv_coverage.py` - Analyzes which columns are present/missing across files ([details](TSV_COVERAGE_ANALYSIS.md))
- `create_coverage_issues.py` - Generates GitHub issue templates for tracking coverage gaps

**Why**: Understanding column coverage helps prioritize data enrichment efforts and identify systematic gaps.

## Processing Order

When processing new data files, follow this recommended order:

1. **Standardize column names** (fix_process_id, fix_n_aligned)
2. **Parse structured identifiers** (parse_sequence_id, parse_mge_params)
3. **Add derived columns** (add_fcleaner_merge_columns, add_metadata_columns)
4. **Remove redundant columns** (fix_filename, remove_backbone_source)
5. **Merge external data** (merge_6p_data, bv_metrics_merger)
6. **Remove unwanted rows** (remove_negative_controls)
7. **Validate coverage** (analyze_tsv_coverage)

## Validation

After processing, all files should:
- Pass header validation tests (`tests/test_tsv_headers.py`)
- Contain all compulsory columns defined in `metadata/headers.tsv`
- Have only recognized column names
- Maintain data integrity (row counts, values preserved)

Run the test suite to verify:
```bash
python -m pytest tests/ -v
```

## Best Practices

### Before Running Scripts

1. **Always use dry-run mode first**: Most scripts support `--dry-run` to preview changes
2. **Work in version control**: Ensure changes can be reviewed and reverted if needed
3. **Understand the issue**: Read the detailed documentation for each script
4. **Check test coverage**: Verify tests exist for the transformation being applied

### After Running Scripts

1. **Review changes**: Use `git diff` to inspect modifications
2. **Run tests**: Ensure all tests pass
3. **Spot check files**: Manually inspect a few modified files
4. **Update documentation**: Document any new patterns or issues discovered
